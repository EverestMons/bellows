## CEO Context

When the daemon stops in the middle of a step — the drain timeout you saw twice on 2026-09-11 — the step's runner dies with it, but every record stays as if it were running: the plan and step rows, the lane file, the worktree, the claim. At the next start the daemon skips such a plan because its worktree still exists, and four hand acts undo it. This plan makes the daemon do what you ruled: at startup it closes that plan cleanly — it keeps any work from the dead step on a `bellows-preserved/` branch, removes the worktree, moves the plan file to `Done/abandoned-…`, marks the plan and its step abandoned, releases the claim — and sends you a notification. It never starts a model run and never redeposits; those stay yours. It refuses to touch a worktree while any live process is still inside it, or when it cannot keep the work first, and a refusal pages you too. Per your rulings of 2026-09-13, the same close covers a plan that `run_plan`'s outer exception left holding its claim, and one whose claim was cut off before its first step (its page says so); and `bellows.py restart` no longer counts a step a previous daemon ran — each step row now records the daemon that ran it — so a refused close can always be retried with a restart. It releases a claim only while that claim is still the run's own. The class is shop-infra, so it holds for your release, and a daemon restart is owed after the merge.

1. **`lifecycle.py` — the steps table learns `abandoned` and the daemon that ran each step.** The `steps` DDL's CHECK (:89) gains `'abandoned'`, and the table gains a nullable `daemon_pid INTEGER` as its last column, before the `UNIQUE(plan_id, step_number)` table constraint — the pid of the daemon that ran the step (items 2 and 7) — for fresh databases. `init_lifecycle_db` (:24) first adds that column when `PRAGMA table_info(steps)` lacks it — `ALTER TABLE steps ADD COLUMN daemon_pid INTEGER`, the way it already adds `plan_doc_ref` (:54–57) — apart from the rebuild, so the column exists even when the rebuild fails and `record_step_start` (item 2) never writes into a table that lacks it (without it every step insert fails, no step row is written, and both idle guards pass a live step — S2-4); ## Why this exists

Census #100091 measured what a drain timeout leaves: the plan row `in_progress`, the step row `running`, the lane file `in-progress-`, the worktree and its branch on disk, the tuyere claim held (Q2) — and no mechanism that restores all of it (Q3). `recover_half_claimed`'s in_progress arm (plan 54) takes a present worktree for a live run — "a legitimately-running step has its worktree" — but at startup the previous daemon is gone — the flock guard admits one (P1) — and under launchd its process group dies with it, the model child included (runner.py starts the child in the daemon's group; the plist carries no `AbandonProcessGroup`; the census's two transcripts end on the drain's own second). The child's tool processes can outlive it — Claude Code's Bash tool starts each shell in its own process group — and so can every child of a daemon started outside launchd (the dashboard's `_spawn_child`, `_perform_restart` without the agent, both `start_new_session=True`). The close's live-process guard is therefore the protection against removing a worktree under a live writer, not a belt on a guarantee. Meanwhile the arm skips exactly the plans it exists for, at every restart. The CEO ruled the fix on 2026-09-11 — close cleanly at startup and notify — and on 2026-09-13 extended it to `run_plan`'s outer-exception hold.

## What this does NOT do

- It does not change the SIGTERM drain or add a drain-side mark (the ruling's options 1 and 3, not taken), and it starts no model run: no resume, no redeposit, no release — those stay the CEO's.
- It does not change the claimed arm; a plan the arm promotes in the same pass is closed like an abandoned runner, its page saying it never started (the CEO's ruling of 2026-09-13 on S1-3). It does not touch a plan whose lane file is `parked-`, `verdict-pending-` or `halted-`, or any state but `in_progress`.
- It does not change `tools/reconcile_plan.py` (thread 317), the claim gate's decline logging (thread 315) or the watcher's placeholder resolution (thread 316).
- It does not tell an outer-exception hold from a runner that died with its daemon: both leave the step `running` and the lane `in-progress-`, and both are closed (the ruling of 2026-09-13); telling them apart would need a marker `run_plan`'s `except` writes, outside this plan.
- It does not change `_discover_holder`'s bare `lsof` (bellows.py:248): it runs only inside `bellows.py stop|restart`, from a terminal or the dashboard, never in the launchd job.
- It does not change `_create_worktree`'s own stranded cleanup, which meets the same plain-directory exposure on a redispatch of the same slug — split to a thread of its own, named in the register; the MUST-PRESERVE keeps that path as today.
- It does not change what today's branch writes for a plan with none of the three lane files — the plan row `abandoned`, its `running` step untouched — so a hand-moved lane can still leave a running phantom; the reconcile tool's LIST shows it, and `--apply` moves it (item 9).
- It does not teach tuyere's `release` to check the holder: the close reads the holder first (item 5), and the verb's own check is thread 328.
- It does not edit doctrine; the three follow-ups in the Post-close are CEO acts.
- It does not write the live database from the DEV or QA step: the migration's first live run is the CEO's restart, and the three historical phantoms move when the Planner runs `--apply` after it.

## MUST-PRESERVE

- ⛔ **Nothing is deleted before it is kept.** The worktree goes only after its uncommitted work is committed on its branch and every un-landed commit — HEAD's line and the `bellows-wt/<slug>` tip alike — sits on a `bellows-preserved/` branch; a directory that is not its own repository, a live process in the worktree, an unreadable process list, a failed snapshot or a failed preservation refuses the close with every surface as it was — save a `bellows-preserved/` branch a failed preservation made before failing, which is kept work, named on the page — and no git command of the close runs anywhere but inside the worktree's own repository (a snapshot commit, once made, stays on the worktree's HEAD — `bellows-wt/<slug>`, or the detached HEAD a step left). Not kept, and named as losses rather than oversights: ignored files — `git add -A` skips what `.gitignore` names (in bellows: `logs/`, `lifecycle.db*`, `bellows.db`, `.env`, `config.json` and others; on the mini `.gitignore` is the only ignore source) — the worktree's HEAD reflog, which `worktree prune` drops (commits reset away inside the step), and the contents of any repository nested in the worktree, which `git add -A` records as a gitlink only.
- ⛔ **No merge.** An abandoned run's branch never reaches `main`; the close never calls `_teardown_worktree`.
- ⛔ **Only the run's own claim and receipts go.** A claim is released only while this machine holds it and no newer plan holds its placeholder; a receipt is retired only when written before the plan was claimed (item 5).
- ⛔ **Only an abandoned runner is closed:** a plan in `in_progress` with its `in-progress-` lane file — a runner that died with its daemon, `run_plan`'s outer-exception hold, or a plan the claimed arm promotes in the same pass (the rulings of 2026-09-13) — or its `Done/abandoned-` file mid-close. A `parked-` plan is skipped; every other state is untouched.
- ⛔ **Today's other paths behave as today:** the claimed arm; the in_progress branch for a plan with no lane file (the four `TestInProgressStrandRecovery` tests pass unchanged); `_create_worktree`'s stranded cleanup (`tests/test_worktree.py`'s stranded tests pass unchanged); the idle guard for a step the running daemon started (`tests/test_stop_path.py`'s existing tests pass unchanged).
- ⛔ **The migration keeps every row and id,** runs once, writes its backup first, and on failure rolls back, logs, and lets the daemon start — and while it has not run, the close refuses; `daemon_pid` is added apart from it, so a failed rebuild never breaks a step write.
- ⛔ **No live database write from the DEV or QA:** test databases under `conftest.isolate_lifecycle_db`, and a backup-API copy; no test reaches the canonical `.bellows-cache/` (the close tests patch `SHADOW_CACHE_DIR`) or leaves a child process running.
- ⛔ **Every `expect_fail` is a class-qualified node id where the test is a method,** and the mutation run is redirected into its deposit, never piped.
- ⛔ **The thread-262 stop:** a QA step that must change production code STOPS and requests a verdict.
