## CEO Context

When a plan's run is lost — a dead runner, a wedged worker — the Planner reconciles it by hand with `tools/reconcile_plan.py`: it closes, halts or abandons the plan's database row, closes its open verdicts and archives its pending verdict requests, in one transaction, then prints the file acts for someone to do. Thread 317 measured three things it leaves wrong. It never touches the plan's steps rows, so a step whose runner died stays `running` for good — the census found two such phantoms. It never releases the plan's tuyere claim, so the same deposit cannot be claimed again without a hand release. And it prints a `git mv` for a file that never exists — `executable-<id>.md` — where a claimed plan's file is `in-progress-…` or `verdict-pending-…`, and an abandoned plan's convention is `Done/abandoned-…`. This plan makes the tool show the steps rows before it writes, mark a running step `abandoned` (the daemon's word for a lost runner) and, on a close, an awaiting step `complete` (as a continue-to-done does), print the exact tuyere command that releases the claim, and print the move from the file that actually exists to where the daemon would have put it, with a commit that takes that move and nothing else the project has staged. It still performs no git act and no claim act itself — the thread offered either, and the tool's contract since #566 keeps every such act the operator's; that choice is yours (open fork 1). The class is shop-infra, so it holds for your release; nothing needs a restart.
