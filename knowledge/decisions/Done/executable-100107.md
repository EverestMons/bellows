## CEO Context

Before the daemon runs a deposited plan, its claim gate asks tuyere for the plan's claim; a decline — another machine holds it, or a claim stranded on this one — stops the run, and the file stays in the lane for the next rescan. Thread 315 measured what that looks like in the log: the gate reports a decline once and then never again while the file sits there, because it remembers the last outcome per plan and stays quiet on a repeat; and every rescan, about every 33 seconds, logs `⏳ detected plan`, `⏳ RUNNING` and `▶ started` — the start logged by the dispatcher after it spawned the run, whatever the gate then decided. On 2026-09-11 a redeposit's decline was logged once, at 15:59:56, with the recovery hint; its next two rescans, at 16:00:17 and 16:00:50, each logged `⏳ detected plan`, `⏳ RUNNING` and `▶ started` and no decline while the file sat in the lane, and the rescan at 16:01:23 passed the gate and ran. The quiet is by design — the claim shim (#570) logs each state once, so that a file declined every 33 seconds does not fill the log — and this plan keeps a bound on it rather than removing it: a repeated decline logs again at most every five minutes, with how many rescans it has declined since the first and the same recovery hint, a successful claim ending the episode; and the plan moves `▶ started` into the run itself, logged once the gate, the mint and the zero-step skip have passed. Two choices are yours: the five-minute interval (open fork 1), and the two `⏳` lines, which still print on every declined rescan in this draft (open fork 2). The class is shop-infra, so it holds for your release; after the merge your restart makes it live.

## Why this exists

Thread 315 measured two silences that read as progress, and both re-derive at `ff97560` (P1, P2). `claim_gate` remembers the last outcome per slug and logs a decline — with its recovery hint — only when the outcome changes (:133–136, :150), so the second and every later declined rescan of the same file log nothing; and `handle_new_plan` logs `▶ started` after spawning the run thread (:3398), whatever the gate inside that thread then decides. On 2026-09-11 a redeposit's first decline logged its WARN, with the hint, at 15:59:56, and a `▶ started` beside it; its rescans at 16:00:17 and 16:00:50 each logged `⏳ detected plan`, `⏳ RUNNING` and `▶ started` and no decline, while the file sat in the lane, until the rescan at 16:01:23 passed the gate and minted #100082 (P4). Thread 306's fix releases an abandoned runner's claim at startup, removing one cause; a decline for any other — another machine holding the project, a claim stranded inside the claim-mint-rename window — still goes silent after its first rescan.

#570 made the repeat silent on purpose: its memo logs a state once — "repeat silent, change logs anew", its law S1-8 (`Done/executable-570.md:61`) — so that a declined file would not add a line every 30 s (its walk register's W1-1, citing its scout's SC-6: `governance/knowledge/research/walk-register-executable-bellows-claim-shim.md:47`). This plan keeps that bound and ends the silence: a repeat logs at most every 300 s — one line where the rescans make nine — and carries the recovery hint wherever the first line carries it (#570 put it on every exit-3 decline; #100005 withheld it for a project another machine holds). The same memo outlives a proceed, so a slug that declined, then claimed, then declined again in one daemon process logged nothing for the second episode, not even once (z5, red on the base); a proceed now ends the episode.
