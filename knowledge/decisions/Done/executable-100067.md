## CEO Context

`tools/check_deposit.py` (#100060) runs five deposit gates against a worktree before a DEV commit, so a failure is found at the desk and not at the pause. Its first real use (the #100062 draft, 2026-09-10) found the shape it cannot handle: a DEV step with TWO commits — the code and tests first, the mutation run file and the dev-log second — cannot pass the pre-check at its FIRST commit by construction, because rule 22 (a) requires every deposit the step declares to exist (P3), and the dev-log and run file do not exist yet. The draft's first workaround ended the `&&` chain with `;` (so `git add` no longer depended on the suite's exit — thread 264's second half); the fold that replaced it, `( check_deposit.py … 2>&1 || true ) | grep -E '^(FAIL|PRECHECK)'`, keeps the chain but accepts a FAIL line as success, so at the first commit the pre-check reports two expected failures and gates nothing but its own crash (P1: five drafts and three Done plans carry it today). Thread 264 named the fix: a stage-aware form where the caller declares the deposits its commit does not write yet, rule 22 (a) skips exactly those and still checks the rest, and the two gates that READ those files go N/A instead of failing on their absence. This plan is that flag, with one guard the thread implies: a path declared missing that exists on disk is a FAIL, so the flag cannot be left on the second commit.

## Why this exists

A pre-check that cannot pass at the moment it is meant to run gets defanged, and a defanged check is the class thread 265 measured (a line nobody reads). The two-commit DEV is the shop's shape (the manifest rides the first commit so the mutation sandbox can see it; the run file and dev-log ride the second), so the first commit is the common case, not an exception. The flag says what the caller knows — which deposits this commit does not write — and the tool checks everything else at full strength; the present-path guard keeps the flag honest at the second commit.
