## Why this exists

The `commits` table is the record a per-step reading trusts — the census's Q2/Q5, the forge reporter's cost-per-step, the "what did the DEV commit" question at a verdict read; today it answers "the merge step" for every commit of a two-step plan. The daemon already computes each step's range; recording it where it is computed is the whole fix.

## What this does NOT do

- Rewrite the 172 historical rows — `steps` carries no sha, the ranges are gone; the glossary names the boundary (Post-close).
- Touch `_teardown_worktree`'s enumeration or the merge-site calls; their list is the branch's own commits (enumerated before the merge), so after this plan they insert nothing in a normal run and everything for a step whose range was unreadable.
- Record uncommitted work — a step that commits nothing records nothing (`pre_diff == post_diff` → `[]`), as before.
- Change `step_files`, the gates, or the pause-side writes.
- Lose a commit when a step's range cannot be read (`pre_diff` or `post_diff` empty, `rev-list` failing): the step records nothing and the merge site records the whole list under the merge step, as today.

## MUST-PRESERVE

- ⛔ **The dedupe is plan-scoped, never global.** Two plans that land the same sha (a cherry-pick, a revert-and-reland) each keep their row; the join is through `steps.plan_id`.
- ⛔ **No live DB write from the plan.** Every test runs under `conftest.isolate_lifecycle_db`; the QA reads a COPY of the live DB through the backup API.
- ⛔ **The run_plan tests read the row.** t7 and t8 assert `commits` rows after `run_plan` returns; the call-count assertion in t7 is the second assertion, never the only one.
- ⛔ **Every `expect_fail` is a class-qualified node id where the test is a method**, and the mutation run is redirected into its deposit, never piped.
- ⛔ **The thread-262 stop:** a QA step that must change production code STOPS and requests a verdict rather than committing.
