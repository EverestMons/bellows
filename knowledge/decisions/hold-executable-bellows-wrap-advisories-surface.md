## CEO Context

The wrap check prints warnings that block nothing. That is its funnel law (`wrap_check.py:458`): advisories are printed, never appended to the fails. But both hooks that run it throw its output away whenever it passes (P1, P2), so a warning is seen only when something else fails at the same time, and on a clean run it is never seen. That mattered once #100128 went live: two of its outcomes — a published tip it could not read, and a crash inside its own arm — PASS with only a warning, so a check that judged nothing looks exactly like one that judged everything.

**CEO ruling 2026-09-18 on thread 427 — SURFACE ALL.** When the check passes but prints warnings, every one reaches a reader: the session-start hook adds them to the session's context, and a passing wrap shows them as a message. Warnings still never block. The ruling is recorded as a `noted` event on thread 427.

**Measured before this draft, and wider than the ruling's note.** The note named the four `WARN (advisory)` lines. Enumerated from the checker's own `print` calls (P4), a PASSING run can print five kinds of line that are not OK: warnings spelled two ways, arms that could not run, a pending-receipt note — and, most important, the line the checker prints when it has CRASHED and passed anyway (`:673`). Only three of its print sites are OK status lines. So the hooks do not select warnings by any spelling: they surface EVERY line a passing run printed EXCEPT its OK lines. A deny-list fails loud — a line added later surfaces by default — where an allow-list fails silent, and failing silent is the defect this plan exists to end. Re-measured for that whole class on both machines (P11): no line of it prints on a normal pass today, so surfacing it changes nothing visible until one does.

**The obligation and its keying (DRAFTING_CYCLE clause (d)).** The obligation, with no mechanism vocabulary: *whatever the wrap check says on a passing run, other than that it passed, is seen by someone who can act on it.* It is keyed to **a reader seeing the line**. This plan's checks — the tests and QA's live run — are keyed to **the hook's output carrying the line in the field the harness reads**. The nouns differ, so the check is a PROXY, and the proxy is argued here rather than assumed (P5): for the session start, the field is the one this hook already uses for debt, and its arrival in the model's context is MEASURED — this session's own start carried it; for the stop hook, the field is documented as a message shown to the user, but which surfaces display it — the desktop app's Code tab included — is NOT documented. So the session-start channel is the one with measured delivery, and it carries every warning that does not depend on the wrapping session's id, because the session-start call runs the same arms — all but the receipts arm's pending-evaluation Note (`wrap_check.py:627`), which prints only for the session that armed the receipt, so its one channel is the stop message (measured: the next session's start prints `OK — no deposits in this session` instead); the stop message is the timely one. ⛔ **The Planner's verdict item — both channels observed live, which needs a PLANTED advisory, because none prints on a normal pass today (P11).** The change is live from the merge, so at the verdict review, ON THE MINI — its memory directory is not a git repository (measured 2026-09-18), whereas on a machine whose memory directory is one, such as the Air, a new file there is an uncommitted memory entry that FAILS `[4/memory]` and blocks the wrap instead of printing an advisory — the Planner creates `verdict-probe-orphan.md` in `$ELUVIAN_WRAP_MEMORY`, a file `MEMORY.md` does not reference, only after confirming that no file of that name exists, so the `[4/memory]` orphan advisory prints; runs `/wrap` in a session whose other arms pass; and at the pass the CEO confirms the stop hook's message is visible in the desktop app's Code tab. A session started while the file exists carries the same line in its session-start context. Then the Planner deletes that file — the one it created. A stop message the app does not display leaves the session-start channel, whose delivery is measured, carrying the obligation for every line but the pending Note, which then reaches no reader — reported to the CEO as the proxy's gap, never waived: the Planner records it, the Note's loss named, as a note on thread 427 before this plan closes.
