## Why this exists

Exec-100001 shipped the arbitration substrate; nothing consumes it. The census measured why that matters: bellows claim safety across machines is pure partition, config-local and invisible, and any plan that is not strict shop work waits for its one partition owner. This plan wires the consumer half the rulings shaped: the global claim in the claim block (after the clearance re-check, before the mint, so a lost claim costs no id and no rename), the R4a COMPLETION-RELEASE at every terminal transition (the claim lifecycle is claim → run → release-at-terminal; sweep and manual are failure lanes), and the per-machine mode gate that makes the census's stage-1/2/3 rollout an explicit config act instead of a code change.

## What this plan does NOT do

- **No tuyere edits.** The substrate is exec-100001's, shipped; this plan only calls it through the seam.
- **No activation, no partition change.** The mode key defaults to `off` — a machine without the key runs BYTE-IDENTICAL claim behavior. Turning a machine to `advisory` (stages 1–2) or `required` (stage 3), and populating tuyere-side `eligible_classes`, are the CEO's per-machine config acts (the exec-A activation law). `watched_projects` moves at stage 3 only, a separate CEO act gated on `required` mode being live.
- **No stale-arm keepalive.** R4a defers the periodic claimant keepalive (which honestly activates stale-release) to a later small plan once claim cadence data exists; this plan ships completion-release + down-sweep consumption only, and says so.
- **No suppression of partition safety.** In `advisory` mode the partition remains the operative guard: a seam ERROR proceeds under partition with a loud warning. A seam DECLINE (exit 3/4) is AUTHORITATIVE in EVERY mode — another machine holds the slug, or this machine's class list forbids it; proceeding past a decline is never legal.
- **No new heartbeat writers, no DB client in bellows.** The seam is the only DB path (the 560 precedent); psycopg stays out of the bellows venv.

## MUST-PRESERVE

- ⚠️ **ABSENT KEY = BYTE-IDENTICAL CLAIM-PATH BEHAVIOR (S3-2 scoped).** `plan_claim_lock` missing or `"off"` → the shim makes NO subprocess call in the CLAIM path (a test proves the claim seam is never invoked in off mode). Releases are NOT mode-gated (S1-5): terminal releases attempt in every mode — best-effort, checkout-unresolvable machines stay quiet — so a rollback to off never strands in-flight claims. An UNRECOGNIZED value → treated as `required` with a loud warning (fail toward safety, never silently unprotected).
- ⚠️ **A DECLINE IS AUTHORITATIVE IN EVERY MODE.** Seam exit 3 or 4 → this machine does NOT claim: log, leave the deposit file untouched for the eligible/holding machine, return. Only seam ERRORS are mode-dependent: `advisory` → loud warn + proceed under partition; `required` → no claim, loud log.
- ⚠️ **RELEASE IS BEST-EFFORT, FAIL-OPEN, AND NEVER BLOCKS A TERMINAL TRANSITION.** A release failure logs loudly and returns; the Done-move/halt proceeds regardless (the stale claim is the sweep/manual lanes' job). PARK IS NOT TERMINAL — a parked plan keeps its claim (it auto-resumes); no release call on the park path, stated not implied.
- ⚠️ **PATH RESOLUTION IS NEVER A LITERAL** (the 560 shop lesson): the tuyere checkout resolves via the Z6 order at call time; subprocess args are a fixed list (no shell), cwd the resolved checkout, timeout 10s hard.
- ⚠️ **`bellows.py` is the live daemon on both machines** — `py_compile` after every edit; the full existing suite must pass unchanged in off mode (the default is the no-op proof).
- ⚠️ **EVERY DATE IS A FIXED LITERAL.**
