## Context

Component 3 of the routed cycle-automation proposal (§5–§7): the **in-bellows depositor + dashboard UI**. It watches a staging area, re-runs `cycle_check` + `plan_lint` on a bar-met plan, reads its `## Cycle Manifest` stanza (mandated by 2a, shipped as v2.12), computes `writes∩writes` (HARD-HOLD) / `reads∩writes` (HOLD) collisions against in-flight plans, then either AUTO-DEPOSITS (`read-only` class) or writes `HOLD: <reason>` (`governed-tooling` / `register-writing`). A dashboard element surfaces cleared/held deposits + reasons.

**Routed decisions (ratified 2026-08-19, do not relitigate):** built INTO bellows (not a standalone `depositor.py`), reusing bellows' own queue / `id_sequence` / freeze / disk state; the `ready/` boundary is a **lifecycle staging state the daemon is forbidden to claim**, not a loose directory; a dashboard UI element on `dashboard.py`; auto-deposit `read-only` only, HOLD executables/register-writers; no cost escalation; ESCALATE is a resumable pause.

**This is a READ-ONLY design diagnostic** (like `diagnostic-472` for 2a): it reads the bellows internals, produces the finalized design + Rule 27 Gap Assessment a T2 executable implements WITHOUT re-verification (T-7), and changes no code. ⚠️ **The executable it authorizes is T2** — the depositor is a standing thing that can pull the dispatch trigger (proposal §5's own worry: "a standing session with write access to a real `knowledge/decisions/` is an autonomous dispatcher"), so the diagnostic's safety analysis is load-bearing.
