## CEO Context

When the daemon re-dispatches a plan and finds that plan's old worktree still on disk, it cleans it up first: it keeps the worktree's un-landed commits on a `bellows-preserved/` branch, removes the directory and deletes the `bellows-wt/<slug>` branch. Thread 322 found the case that loses work: when the path is a plain directory — a worktree whose `.git` file is gone, or what a half-finished removal leaves — every git command run in it answers for the canonical checkout instead, so the cleanup reads `main`'s HEAD as the worktree's, keeps nothing, and deletes `bellows-wt/<slug>` with its un-landed commits. The prototype reproduced it on today's code, and found a worse one: when the path is a symlink to another plan's live worktree, the removal follows the link and deletes that worktree, its uncommitted work included (x16). This plan makes the cleanup read no HEAD it cannot prove is the worktree's own — the startup close's toplevel test, made by inode and without its registration requirement — read a detached HEAD from the project's own worktree registration when the directory has lost its link, keep the branch tip whenever it is off `main`, and never hand a symlink to the removal. As you ruled, a save that fails removes nothing: the cleanup stops the dispatch itself, at the existing "worktree creation failed" pause, and its message names what was left and what to do — the prototype's first version returned instead, and the daemon's next command then created an empty branch that paused the following dispatch a second time. A path the removal could not clear stops the dispatch the same way, once its commits are kept, and a dangling symlink — what x16's link becomes once its target is gone — now reaches the cleanup instead of making that empty branch. One premise of your ruling moves: it was asked as "the plan stops before its first step", but the cleanup runs on every dispatch, a resumed step's too, and today's pause always says step 1, so a `continue` would re-run a finished DEV step. The draft pauses at the step dispatched, and at a plan's final step a `continue` retries that step instead of closing the plan to Done without running it — so `stop`, not `continue`, is what ends such a plan. You ruled it so on 2026-09-15 (open fork 5).
