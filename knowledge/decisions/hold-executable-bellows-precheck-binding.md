## CEO Context

You ruled that a step's commit be bound to a passing pre-check by a hook that refuses the commit, and that the hook bind only a step whose text names `check_deposit.py`. The plan does it in three parts. The pre-check, on a clean run, records in the worktree's own git directory the content of every path that differs from the last commit, and removes that record when a run fails. The daemon, dispatching a bound step, puts variables in the agent's environment that point git's hook directory at a new hook in bellows — nothing is written to any repository's configuration. The hook refuses a commit unless every path it changes carries the recorded content: a commit made without the pre-check, or after an edit made since its last passing pre-check, stops at the desk, before any gate, and the refusal names the exact command to run — with the stage flag a first commit needs. Then it runs the repository's own pre-commit, so the governance repository's walk-register check still runs. Measured (P5, P7): an agent's own shell inherits the variables; a real agent in a bound scratch worktree was refused, ran the command the refusal printed, and committed; #100097's DEV made four commits and ran the pre-check before none — each would have been refused, and two of them, made after a mutation run that recorded survivors, pass only once that run file is removed, which the refusal now prints. ## Why this exists

Thread 333: a plan's commit item is a shell chain — `pytest tests/ -q && check_deposit.py <lane> <step> --wt … && git add … && git commit …` — and nothing makes an executor run it as one. #100097's DEV made four commits and ran the pre-check before none of them (P7), and was halted at the pause by the gates the pre-check would have run at the desk; #100098's steps ran each link as a separate command, in order, by the agent's choice. Today the chain's order is enforced by the verdict read alone, after the teardown has merged the step's commits. The binding makes the pre-check's pass a precondition of the commit itself, at the one point a commit cannot route around — git's own pre-commit hook — for the steps whose plans declare the chain (the CEO's reach ruling). It does so without writing any repository's configuration: the daemon hands the hook directory to the agent through its environment, which the agent's shell inherits (P5), so the daemon's own commits and every other process are untouched.

## What this does NOT do

- It does not stop a commit the hook never sees — `--no-verify`, `cherry-pick`, `revert`, `rebase`, `merge`, `am`, `commit-tree` with `update-ref`, a `-c core.hooksPath` override, a commit with the binding's variables unset — and nothing records one (open fork 1); nor does it bind the suite link: a commit after a passing pre-check and no suite run goes through (P7: #100099's DEV piped its suite through `tail -3`, so its exit gated nothing).
- It does not bind a step whose text does not name `check_deposit.py` — forge cycles run as today (P6).
- It does not change a gate, the pause or the teardown, and the daemon's own commits carry no binding.
- It does not keep a refused change: work left uncommitted when a step ends is lost at the teardown's `git worktree remove --force` (`bellows.py:2966`), `_auto_stage_deposits` committing only the step's declared deposits — the refusal says so, and a guard at the pause is open fork 5.
- It does not write any repository's git configuration or any file under a `.git/hooks` directory.
- It does not fix thread 309 (open fork 2).
- It does not chain any hook but pre-commit (open fork 3).
- It does not write the doctrine texts (the CEO's apply act, quoted in Post-close).
